## この文書の役割

### 目的
fortuneP に存在する複数の agent 文書を、役割一覧ではなく、実運用できる流れとして定義する。

### 何をするか
- どのフェーズで誰を主担当にするかを定義する
- どの順番で視点を通すかを定義する
- 何を入力にし、何を出力するかを定義する
- 役割が衝突したときの優先順位を定義する
- チャット段階と repo 反映段階の境界を定義する
- 1テーマを最後まで回す標準運用を定義する

### 誰が主担当か
- 全体統合者としての専属エージェント
- 各フェーズでは、その時点の主担当 agent を切り替えて運用する

### 何を入力にするか
- `docs/agents/*.md`
- プロジェクト概要
- MVP方針
- 世界観の核
- 占星術の核
- 進行原則
- 直前フェーズの出力物

### 何を出力するか
- 次の担当へ渡せる中間成果物
- チャットで壁打ちできる提案
- repo に反映してよい粒度の仕様、設計、実装差分

### 次に渡す条件
- 現フェーズの出力が、次フェーズの入力として読める形に整理されていること
- 未確定事項と確定事項が分離されていること

## operation-model が必要な理由

### 目的
複数の agent 文書を置いただけでは、実際の運用順と判断基準が曖昧になるため、それを防ぐ。

### 何をするか
この文書では、fortuneP の agent 群を以下の問題に答えられる状態にする。

- 今は誰の視点で考えるべきか
- 何を決めたら次へ進めるか
- どこまで自走してよいか
- 何はユーザー確認が必要か
- どの出力なら repo へ反映してよいか

### 誰が主担当か
- 専属エージェント
- 必要に応じて agent ロールを順番に切り替える

### 何を入力にするか
- 現在のテーマ
- 現在地（企画 / 設計 / 実装 / レビューなど）
- 既存決定事項
- 未決事項

### 何を出力するか
- 迷わない進行順
- 迷わない責任分担
- 迷わない判断基準

### 次に渡す条件
- 各フェーズの責任範囲が曖昧でないこと
- 受け渡し時に情報が欠落しないこと

## 基本思想

### 目的
fortuneP の agent 運用における最上位原則を固定する。

### 何をするか
すべての agent は、以下の思想に従って動く。

1. 機能先行ではなく感情先行で考える  
2. ただし、雰囲気のために意味と使いやすさを壊さない  
3. MVPでは広げるより、結果ページの価値を深める  
4. PC前提ではなく iPhone 前提で考える  
5. 1回で完璧にしようとせず、順番に視点を通して精度を上げる  
6. 並列実行を前提にせず、擬似マルチエージェントとして順次運用する  

### 誰が主担当か
- すべての agent に共通する最上位原則
- 最終判断は専属エージェントが統合して行う

### 何を入力にするか
- プロジェクト全体方針
- 世界観の核
- 占星術の核
- MVP方針
- 進行原則

### 何を出力するか
- 各 agent の判断の土台
- 衝突時の共通参照軸

### 次に渡す条件
- 各提案がこの思想と矛盾していないこと

## 擬似マルチエージェント運用の前提

### 目的
実際には複数 agent を並列稼働できない前提を明文化し、無理のない運用にする。

### 何をするか
fortuneP では、以下の方式で agent を運用する。

- 1つの専属エージェントが作業する
- その中で必要な役割に順番に切り替える
- 各視点を通した後、最後に統合案を出す
- 同時並列ではなく、明確な baton pass で前進する

### 誰が主担当か
- 常に専属エージェントが最終統合者
- 個別フェーズでは主担当 agent のロールを優先する

### 何を入力にするか
- 現在の課題
- 現在のフェーズ
- 既存成果物
- 前フェーズの出力

### 何を出力するか
- 今どのロールで考えているか
- 次にどのロールへ渡すか
- どこまでが確定で、どこからが未確定か

### 次に渡す条件
- 1回の出力で役割が混線しすぎていないこと
- 統合前に主要視点を最低限通していること

### 運用上の原則
- 一度に全 agent の意見を同列に並べない
- まず主担当を決める
- 補助担当は主担当の不足を補う
- 最後に専属エージェントが統合する

## フェーズごとの主担当 / 補助担当

### 目的
企画からレビューまで、各フェーズの責任者を明確にする。

---

### 1. 企画

#### 目的
何を作るかではなく、何を感じてほしいかと、MVPで何を絞るかを定める。

#### 何をするか
- テーマ整理
- 体験価値の定義
- MVPへの圧縮
- 優先順位づけ

#### 誰が主担当か
- 主担当: `product-planner`
- 補助担当: `astrology-researcher`, `content-architect`, `growth-marketer`

#### 何を入力にするか
- プロジェクト概要
- 世界観の核
- ターゲット
- MVP方針
- 占星術の核

#### 何を出力するか
- 企画の目的
- 対象ユーザーの感情ゴール
- MVPで扱う範囲 / 扱わない範囲
- 画面や機能の優先順位

#### 次に渡す条件
- テーマが広すぎず、MVPに落ちていること
- 結果ページを中心に価値が整理されていること

---

### 2. 壁打ち

#### 目的
企画案や発想を粗いまま出し、危うさや浅さを早い段階で見つける。

#### 何をするか
- アイデアの言語化
- 体験の弱点発見
- 世界観と意味のズレ検出
- 方向性の比較

#### 誰が主担当か
- 主担当: `product-planner`
- 補助担当: `ux-ui-designer`, `astrology-researcher`, `content-architect`

#### 何を入力にするか
- 企画メモ
- ざっくりした画面案
- 仮コピー
- 仮導線

#### 何を出力するか
- よい点
- 危ない点
- 深めるべき点
- 捨てるべき点
- 次に詰めるべき問い

#### 次に渡す条件
- 方向性が1本に絞れていること
- まだ未確定でも、次に設計へ進める材料があること

---

### 3. 修正

#### 目的
壁打ちで見えたズレを修正し、次の設計に耐える案へ整える。

#### 何をするか
- 世界観の粗さを直す
- 占星術的な雑さを直す
- 情報設計の破綻を直す
- モバイル負荷を減らす

#### 誰が主担当か
- 主担当: 課題の種類で変える
  - 体験のズレが中心なら `product-planner`
  - 導線や画面のズレが中心なら `ux-ui-designer`
  - 意味のズレが中心なら `astrology-researcher`
  - 言葉のズレが中心なら `content-architect`
- 補助担当: `breaker-qa`

#### 何を入力にするか
- 壁打ち結果
- 修正対象の案
- 問題点一覧

#### 何を出力するか
- 修正版の方向性
- 修正版の要件
- 直した理由
- まだ残る保留点

#### 次に渡す条件
- 設計に進めるだけの一貫性があること
- 修正意図が言語化されていること

---

### 4. 設計

#### 目的
企画を実際に作れる構造に分解する。

#### 何をするか
- 情報設計
- 画面構成
- コンテンツ構造
- 技術構成
- 実装単位の整理

#### 誰が主担当か
- 主担当: `technical-architect`
- 補助担当: `ux-ui-designer`, `content-architect`, `astrology-researcher`

#### 何を入力にするか
- 修正版企画
- 優先画面
- ユーザーフロー
- 必要な占星術要素
- 必要なコンテンツ要素

#### 何を出力するか
- 画面単位の構成
- データ / ロジックの要件
- コンポーネント方針
- 実装ステップ
- 実装前提の制約

#### 次に渡す条件
- フロント実装可能な粒度まで分解されていること
- 曖昧な表現だけで終わっていないこと

---

### 5. 試作

#### 目的
設計を、見える形・触れる形にする。

#### 何をするか
- UI試作
- フロント実装
- 仮データ投入
- 結果ページ体験の具体化

#### 誰が主担当か
- 主担当: `frontend-engineer`
- 補助担当: `ux-ui-designer`, `content-architect`, `technical-architect`

#### 何を入力にするか
- 画面設計
- コンポーネント方針
- コピー案
- 実装範囲

#### 何を出力するか
- 実装差分
- 画面の見た目
- 仮動線
- 不足している要素の洗い出し

#### 次に渡す条件
- レビュー可能な形で触れること
- 見た目だけでなく導線も確認できること

---

### 6. レビュー

#### 目的
壊れている点、浅い点、ズレている点を発見する。

#### 何をするか
- 破綻確認
- モバイル使用感の確認
- 世界観破壊の確認
- 占星術的違和感の確認
- コピーの刺さり方の確認

#### 誰が主担当か
- 主担当: `breaker-qa`
- 補助担当: `ux-ui-designer`, `astrology-researcher`, `content-architect`, `product-planner`

#### 何を入力にするか
- 試作物
- 実装差分
- レビュー観点
- MVP基準

#### 何を出力するか
- 問題一覧
- 致命度
- 修正優先順位
- 再設計が必要かどうかの判断

#### 次に渡す条件
- 問題が整理され、次の修正担当がわかること
- ただの感想ではなく、修正可能な指摘になっていること

---

### 7. 完成直前整理

#### 目的
公開前に、伝わり方・計測・将来拡張の余地を最低限整える。

#### 何をするか
- コピー最終整形
- CTA整理
- シェア導線整理
- 最低限の計測設計
- MVPとして不要なものの削除

#### 誰が主担当か
- 主担当: `product-planner`
- 補助担当: `growth-marketer`, `analytics-experimenter`, `content-architect`, `monetization-strategist`

#### 何を入力にするか
- レビュー反映後の試作
- 導線
- CTA
- シェア案
- 計測したい仮説

#### 何を出力するか
- 公開直前チェック結果
- CTA / シェア / 計測の整備内容
- MVPに残すもの / 削るもの
- 公開後の次アクション候補

#### 次に渡す条件
- MVPを壊さない範囲で整理が済んでいること
- 不要な欲張り追加が入っていないこと

## baton pass のルール

### 目的
役割切り替え時の情報欠落を防ぐ。

### 何をするか
agent を切り替えるたびに、以下を必ず明示する。

1. 今のテーマ  
2. 現在のフェーズ  
3. 直前までの確定事項  
4. 未確定事項  
5. 今回見てほしい観点  
6. 出力してほしい粒度  
7. 次に渡したい相手  

### 誰が主担当か
- baton を渡す側の agent ロール
- 最終的な整形責任は専属エージェント

### 何を入力にするか
- 直前フェーズの成果物
- 変更理由
- 保留点

### 何を出力するか
- 次担当が迷わず読める引き継ぎ
- 確定 / 未確定の分離
- 作業範囲の明示

### 次に渡す条件
- 「何を考えればいいか」が一目でわかること

### baton pass の最小テンプレート
```md
- テーマ:
- 現在フェーズ:
- 確定事項:
- 未確定事項:
- 今回の主な論点:
- 欲しい出力:
- 次の想定担当:
```

## 衝突時の優先順位

### 目的
agent 同士の意見がぶつかったときに、迷わず判断する。

### 何をするか
衝突時は、原則として以下の順で優先する。

1. 占星術として意味が通っているか  
2. モバイルで使いやすいか  
3. 世界観・ロマン・余韻を深められるか  
4. 実装可能か  
5. 拡散しやすいか  
6. 将来の収益導線として魅力があるか  

### 誰が主担当か
- 最終判断: 専属エージェント
- 意味の最終番人: `astrology-researcher`
- 使いやすさの最終番人: `ux-ui-designer`
- 実装成立の最終番人: `technical-architect` / `frontend-engineer`

### 何を入力にするか
- 衝突している提案
- それぞれの利点 / 欠点
- MVPとの整合性

### 何を出力するか
- 採用案
- 不採用理由
- 後回しにする案

### 次に渡す条件
- 感覚ではなく、優先順位に沿った説明ができること

### 補足ルール
- 「映えるが意味が崩れる」は不採用
- 「雰囲気は弱いが理解しやすい」は一旦採用し、演出で後から補う
- 「作れるが重い」はMVPでは削る
- 「伸びそうだが安っぽい」は採用しない

### チャットで見せるべきもの

#### 何をするか

- 画面構成案
- コピー案
- UI原則案
- 実装前の設計案
- 大きめの変更方針
- 世界観に関わる変更
- 情報設計の再編
- 仕様の意味を変える修正

#### 理由
- iPhoneでも確認しやすい
- 壁打ちしやすい
- いきなり repo を揺らさない
- 意図のズレを早く発見できる

---

### repo反映してよいもの

#### 何をするか
以下は、方針が固まっていれば反映してよい。

- 既に合意済み方針に沿う文言整理
- 軽微なレイアウト調整
- 命名整理
- コメント整理
- 明らかな誤字修正
- 既存仕様の範囲内の実装
- 設計通りの追加

#### 条件
- 新しい意思決定を含まないこと
- 世界観や意味を大きく変えないこと
- 差分理由が明確であること

---

### 原則

- 大きい判断は先にチャット
- 小さい確定作業は repo 反映可
- 「実装はできるが、意味が変わる」ものは先にチャット
- 「見せ方が変わる」ものも先にチャット
- 「単なる整形」は反映可

## 自走してよい範囲 / 勝手に確定しない範囲

### 目的
自走力と暴走防止の境界を明確にする。

---

### 自走してよい範囲

#### 何をするか
以下は自走してよい。

- 既存方針の具体化
- 既存方針の中での優先順位整理
- 軽微な構成整理
- 文書の構造化
- 設計の分解
- 実装順の整理
- 明らかな矛盾の修正
- MVPを守るための削減提案
- 既に合意済みの範囲での改善

---

### 勝手に確定しない範囲

#### 何をするか
以下は勝手に確定しない。

- プロダクトの核体験変更
- 結果ページの意味構造変更
- 占星術解釈の強い言い換え
- ブランドトーンの大幅変更
- ターゲット変更
- MVP範囲の拡張
- 重い機能追加
- 収益化の導入決定
- 計測のために体験を損ねる変更
- UIの主導線を変える大改修

### 判断に迷う場合
迷ったら以下で判断する。

- 既存の決定を具体化しているだけか
- 新しい意思決定を発生させているか
- ユーザーの価値認識を変えるか
- iPhone上でその場確認した方が安全か

1つでも重いなら、先にチャットへ出す。

## 1テーマを最後まで回す標準シーケンス

### 目的
1つのテーマを、迷わず最後まで回す標準運用を作る。

### 何をするか
テーマごとに、原則この順で回す。

1. `product-planner` で目的と優先順位を整理する  
2. `astrology-researcher` で意味破綻がないか確認する  
3. `content-architect` で読ませ方と余韻を設計する  
4. `ux-ui-designer` でモバイル導線と画面構成へ落とす  
5. `technical-architect` で実装可能な構造へ分解する  
6. `frontend-engineer` で試作する  
7. `breaker-qa` で壊しに行く  
8. 必要に応じて 2〜6 へ戻る  
9. `growth-marketer` / `analytics-experimenter` / `monetization-strategist` を完成直前に補助投入する  
10. 専属エージェントが最終統合して、チャット提示 or repo反映判断を行う  

### 誰が主担当か
- テーマの初期定義は `product-planner`
- 最終統合は専属エージェント

### 何を入力にするか
- 今回扱うテーマ
- 目的
- 制約
- 既存決定事項

### 何を出力するか
- 企画からレビューまでの一貫した成果物
- 差分理由
- 次アクション

### 次に渡す条件
- 途中で役割を飛ばしすぎていないこと
- 必要最低限のレビューを通していること

### 典型例: 結果ページを改善する場合
1. 何を感じてほしいかを整理する  
2. 太陽 / 月 / アセンダントの意味役割を確認する  
3. 読む順番と見出しを組み直す  
4. スマホで読みやすい画面密度にする  
5. 実装単位に分ける  
6. 仮実装する  
7. 余韻を壊す点、読みにくい点、意味が浅い点をレビューする  
8. 修正する  
9. シェア導線と最低限の計測を整える  
10. 公開前に不要物を削る

## 一言まとめ

fortuneP の agent 運用は、  
**複数の役割を同時に走らせることではなく、1つの専属エージェントが、適切な順番で視点を切り替えながら、最後に統合すること**  
を基本とする。

そのために大事なのは、以下の3点である。

- まず主担当を決めること
- baton pass を明示すること
- 大きい判断はチャットで見せ、小さい確定作業だけを repo に反映すること
